# Практика: постановка задачи, командная разработка и code review

В этой работе вы пройдёте небольшой командный цикл разработки: сформулируете задачу для другого участника, реализуете чужую задачу и проведёте code review ещё одной работы.

В каждом репозитории есть три разные роли:

- **Автор ТЗ** — владелец задания: получает персональный вариант, формулирует требования и принимает готовый результат.
- **Разработчик** — реализует игру по `TASK.md` и открывает Pull Request.
- **Рецензент** — проводит техническое code review, требует исправления и после исправлений одобряет финальную версию.

Все три роли в одном проекте должны выполнять **разные пользователи**.

Кроме собственной работы каждый студент должен выступить разработчиком в одном чужом проекте и рецензентом — в другом.

---

## 1. Получите персональный вариант

Автор задания создаёт **одну рабочую ветку** в своём репозитории.

После создания ветки автоматически запускается CI и добавляет:

- `VARIANT.md` — персональные ограничения игры;
- `TASK.md` — шаблон технического задания;
- `README.md` — шаблон итогового описания;
- `variant.json` — данные варианта для автоматической проверки;
- каталог `site/` — заготовку браузерной игры.

Если генерация ещё выполняется, дождитесь её завершения и обновите страницу ветки.

> Не изменяйте `VARIANT.md` и `variant.json`.

---

## 2. Сформулируйте техническое задание

Откройте `VARIANT.md`. В нём указаны:

- тематика;
- основная игровая механика;
- обязательная особенность;
- рекомендуемый масштаб проекта.

На их основе придумайте собственную небольшую браузерную игру и заполните `TASK.md`.

В техническом задании должны быть понятны:

- идея игры;
- основная механика;
- правила и цель;
- обязательные требования;
- критерии приёмки.

Критерии приёмки должны описывать **наблюдаемое поведение** программы. По ним автор задания в конце сможет проверить результат.

После заполнения `TASK.md` закоммитьте изменения в рабочую ветку.

---

## 3. Распределите роли

Договоритесь с двумя другими студентами:

- кто будет **разработчиком** вашей игры;
- кто будет её **рецензентом**.

Укажите их GitVerse-логины в `README.md`:

```md
## Командная работа

- Автор ТЗ: @alice
- Разработчик: @bob
- Рецензент: @charlie
```

Автор ТЗ, разработчик и рецензент должны быть разными пользователями.

В этом же README укажите проекты, в которых вы сами работаете в двух других ролях:

```md
## Моя работа в других проектах

- Разработчик для: @diana
- Рецензент для: @eve
```

---

## 4. Передайте работу разработчику

Разработчик продолжает работу **в уже созданной рабочей ветке автора задания**.

Создавать отдельную ветку разработчика для этого проекта не нужно.

Разработчик:

1. читает `VARIANT.md` и `TASK.md`;
2. реализует игру в каталоге `site/`;
3. при необходимости обновляет описание и управление в `README.md`;
4. делает осмысленные коммиты;
5. после готовности **сам открывает Pull Request в `master`**.

Использовать AI-инструменты и coding agents разрешается.

При этом разработчик должен понимать получившийся код и уметь исправить его после замечаний рецензента.

---

## 5. Проведите техническое code review

После открытия Pull Request работу проверяет указанный в README **рецензент**.

Рецензент должен:

1. посмотреть изменения в коде;
2. оставить минимум **два inline-комментария** к конкретным строкам изменений;
3. в итоговом review содержательно описать, что требуется исправить;
4. отправить review со статусом **Request changes**.

Обычные сообщения в обсуждении Pull Request не заменяют inline-комментарии code review.

---

## 6. Исправьте замечания

После `Request changes` разработчик исправляет замечания и делает **новый коммит** в ту же рабочую ветку.

Важно: исправления после review должен внести именно разработчик.

После нового push рецензент повторно проверяет актуальную версию.

---

## 7. Получите техническое одобрение

Если замечания исправлены, рецензент одобряет текущую версию Pull Request через **Approve**.

Approval должен относиться к финальному состоянию ветки.

Если после approval появился ещё один коммит, необходимо проверить актуальную версию ещё раз и при необходимости поставить новый Approve.

---

## 8. Проведите приёмку по ТЗ

После технического review работу проверяет **автор ТЗ**.

Автор:

1. запускает игру;
2. сверяет результат с `TASK.md`;
3. проверяет критерии приёмки;
4. при успешной приёмке также ставит **Approve**.

Таким образом, перед merge у финальной версии должны быть два независимых одобрения:

- рецензента — техническое code review;
- автора ТЗ — приёмка результата.

Разработчик не может одобрять собственный Pull Request вместо одного из этих участников.

---

## 9. Влейте Pull Request

После исправления замечаний и двух актуальных approvals Pull Request можно влить в `master`.

После merge не изменяйте историю Pull Request: она используется итоговой проверкой для восстановления последовательности

`review → Request changes → исправление → Approve`.

---

## 10. Проверьте GitVerse Pages

Готовая игра находится в каталоге:

```text
site/
```

Для GitVerse Pages используется ветка `master` и каталог `/site`.

Проверьте, что опубликованная страница открывается и игра работает.

Для локальных CSS, JavaScript и изображений используйте относительные пути, например:

```html
<link rel="stylesheet" href="./style.css">
<script src="./script.js"></script>
<img src="./assets/example.png" alt="">
```

---

## 11. Запустите итоговую проверку

После merge запустите workflow **«Проверка командной работы»** вручную и укажите номер Pull Request.

Проверка анализирует не только конечные файлы, но и историю командной работы.

Она проверяет, в частности:

- персональный вариант не был изменён;
- заполнен `TASK.md`;
- существуют файлы игры в `site/`;
- в README корректно указаны роли;
- Pull Request создал указанный разработчик;
- technical reviewer оставил inline-замечания;
- был отправлен `Request changes`;
- разработчик сделал новый коммит после review;
- рецензент одобрил финальный HEAD;
- автор ТЗ отдельно одобрил финальный HEAD;
- Pull Request влит в `master`.

Работа считается завершённой после успешной итоговой проверки и работающей страницы GitVerse Pages.
